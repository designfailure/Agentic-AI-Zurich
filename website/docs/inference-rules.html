Inference Rules Guide

Inference rules define the logic for semantic routing, determining when and how components, datasets, and tools are selected based on request characteristics.

📐 Rule Structure

Every inference rule has the same basic structure: 

{
  "id": "unique-rule-id",
  "name": "Human Readable Rule Name",
  "condition": {
    "type": "rule-type",
    "parameters": { /* ... */ },
    "expression": "logical expression"
  },
  "action": {
    "type": "action-type",
    "target": "target-id",
    "parameters": { /* ... */ }
  },
  "priority": 10,
  "confidenceThreshold": 0.7
}

🎯 Rule Types

1. Intent-Match Rules

Match based on detected user intent: 

{
  "id": "query-intent-rule",
  "name": "Route Query Intent",
  "condition": {
    "type": "intent-match",
    "parameters": {
      "intents": ["query", "search", "find"],
      "minConfidence": 0.7
    },
    "expression": "intent IN ['query', 'search', 'find'] AND confidence >= 0.7"
  },
  "action": {
    "type": "select-dataset",
    "target": "primary-database"
  },
  "priority": 10,
  "confidenceThreshold": 0.7
}

2. Keyword-Match Rules

Match based on keywords in the request: 

{
  "id": "database-keyword-rule",
  "name": "Database Keywords Detection",
  "condition": {
    "type": "keyword-match",
    "parameters": {
      "keywords": ["database", "sql", "table", "query"],
      "matchType": "any",
      "caseSensitive": false
    },
    "expression": "ANY(keywords) IN ['database', 'sql', 'table', 'query']"
  },
  "action": {
    "type": "route",
    "target": "database-component"
  },
  "priority": 8,
  "confidenceThreshold": 0.65
}

3. Semantic-Similarity Rules

Match using vector embeddings and semantic similarity: 

{
  "id": "semantic-match-rule",
  "name": "Semantic Domain Match",
  "condition": {
    "type": "semantic-similarity",
    "parameters": {
      "embeddingModel": "text-embedding-3-large",
      "similarityThreshold": 0.85,
      "fields": ["domain", "concepts", "keywords"]
    },
    "expression": "cosine_similarity(context, component) >= 0.85"
  },
  "action": {
    "type": "route",
    "target": "best-matching-component"
  },
  "priority": 15,
  "confidenceThreshold": 0.85
}

4. Pattern-Match Rules

Match using regex patterns for structured inputs: 

{
  "id": "sql-pattern-rule",
  "name": "SQL Query Detection",
  "condition": {
    "type": "pattern-match",
    "parameters": {
      "pattern": "^(SELECT|INSERT|UPDATE|DELETE)\\s+",
      "field": "query",
      "flags": "i"
    },
    "expression": "REGEX_MATCH(query, '^(SELECT|INSERT|UPDATE|DELETE)\\s+', 'i')"
  },
  "action": {
    "type": "invoke-tool",
    "target": "sql-executor"
  },
  "priority": 20,
  "confidenceThreshold": 1.0
}

5. Composite Rules

Combine multiple conditions with AND/OR logic: 

{
  "id": "composite-rule",
  "name": "Multi-Condition Dataset Selection",
  "condition": {
    "type": "composite",
    "parameters": {
      "operator": "AND",
      "conditions": [
        {
          "type": "intent-match",
          "parameters": {
            "intents": ["analyze"]
          }
        },
        {
          "type": "keyword-match",
          "parameters": {
            "keywords": ["financial", "stock"]
          }
        },
        {
          "type": "semantic-similarity",
          "parameters": {
            "similarityThreshold": 0.75
          }
        }
      ]
    }
  },
  "action": {
    "type": "select-dataset",
    "target": "financial-dataset"
  },
  "priority": 12,
  "confidenceThreshold": 0.8
}

⚡ Action Types

Available Actions

  • select-dataset: Choose a dataset
  • invoke-tool: Call a tool
  • route: Route to a component
  • transform: Transform data
  • composite: Execute multiple actions

Composite Actions

{
  "action": {
    "type": "composite",
    "target": "data-processing-pipeline",
    "parameters": {
      "stages": [
        {
          "action": "select-dataset",
          "target": "source-dataset"
        },
        {
          "action": "invoke-tool",
          "target": "data-transformer"
        },
        {
          "action": "invoke-tool",
          "target": "data-validator"
        }
      ],
      "executionMode": "sequential"
    }
  }
}

📊 Priority System

Rules are evaluated in priority order (highest first). Here are recommended priority ranges:

Priority Range Use Case Example
90-100 Exact pattern matches SQL query detection
70-89 High-confidence semantic matches Domain-specific routing
50-69 Intent and keyword matches General query routing
30-49 Fuzzy or partial matches Fallback routing
0-29 Low-confidence fallbacks Default handlers

🎚️ Confidence Thresholds

The confidenceThreshold determines the minimum confidence required for the rule to fire:

  • 1.0: Requires exact match (pattern rules)
  • 0.8-0.9: High confidence required (specific domains)
  • 0.6-0.7: Medium confidence (general routing)
  • 0.4-0.5: Low confidence (broad matches)
  • 0.0: Always fires (fallback rules)
💡 Best Practice: Set higher thresholds for more specific rules and lower thresholds for general fallback rules.

🔄 Rule Execution

The inference engine processes rules as follows:

  1. Sort rules by priority (highest first)
  2. Evaluate each rule's condition
  3. Calculate confidence score
  4. If score ≥ threshold, execute action
  5. Aggregate results from matching rules
  6. Select best match based on confidence

📝 Rule Categories

Organize rules into categories for better management: 

{
  "ruleCategories": [
    {
      "category": "intent-based-routing",
      "description": "Routes based on user intent",
      "rules": [ /* ... */ ]
    },
    {
      "category": "semantic-matching",
      "description": "Matches based on semantic similarity",
      "rules": [ /* ... */ ]
    },
    {
      "category": "keyword-based",
      "description": "Exact or fuzzy keyword matching",
      "rules": [ /* ... */ ]
    }
  ]
}

✅ Testing Rules

Use the evaluation endpoint to test rules without executing: 

curl -X POST http://localhost:3000/evaluate \
  -H "Content-Type: application/json" \
  -d '{
    "intent": "Find customer orders",
    "context": {}
  }'

🎯 Best Practices

  • Specific First: Higher priority for more specific rules
  • Test Thoroughly: Test with diverse inputs
  • Document Logic: Use clear names and descriptions
  • Appropriate Thresholds: Balance precision and recall
  • Avoid Overlaps: Minimize conflicting rules
  • Monitor Performance: Track rule match rates
