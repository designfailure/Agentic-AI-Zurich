Creating MCP Components

Components are the core building blocks of the MCP architecture. Each component is a self-describing module that provides API structures, dataset inference capabilities, and tool calling mechanisms.

🏗️ Component Structure

Every MCP component follows a standard structure defined by the JSON Schema: 

{
  "$schema": "../schemas/mcp-component-schema.json",
  "id": "unique-component-id",
  "type": "source-module",
  "name": "Human Readable Name",
  "description": "What this component does",
  "apiStructure": { /* API definition */ },
  "datasetInference": { /* Dataset selection rules */ },
  "toolCalling": { /* Tool invocation specs */ },
  "semanticContext": { /* Semantic metadata */ },
  "capabilities": [ /* Capability list */ ],
  "metadata": { /* Version info, author, etc */ }
}

📋 Required Fields

1. Basic Information

  • id: Unique identifier (lowercase, hyphen-separated)
  • type: Component type (source-module, tool, dataset, composite)
  • name: Human-readable name
  • apiStructure: API interface definition
  • semanticContext: Semantic metadata for inference

2. API Structure

Define how your component can be accessed: 

{
  "apiStructure": {
    "protocol": "rest",
    "baseUrl": "http://localhost:8080/api",
    "endpoints": [
      {
        "name": "processData",
        "method": "POST",
        "path": "/process",
        "parameters": [
          {
            "name": "input",
            "type": "string",
            "required": true,
            "description": "Input data to process",
            "semanticRole": "input"
          }
        ],
        "returns": {
          "type": "object",
          "semanticType": "processed-result"
        },
        "semanticTags": ["process", "transform"]
      }
    ],
    "authentication": {
      "type": "apiKey",
      "configuration": {
        "headerName": "X-API-Key"
      }
    }
  }
}

3. Semantic Context (Critical!)

This is the most important part for semantic inference: 

{
  "semanticContext": {
    "domain": "data-processing",
    "intents": [
      "process-data",
      "transform-data",
      "convert-data"
    ],
    "keywords": [
      "process",
      "transform",
      "convert",
      "data",
      "format"
    ],
    "concepts": [
      "data-transformation",
      "format-conversion"
    ]
  }
}
💡 Best Practice: Include as many intents and keywords as possible. Think about different ways users might express their needs. Include synonyms and variations.

🎯 Dataset Inference

Define datasets and rules for automatic dataset selection: 

{
  "datasetInference": {
    "inferenceType": "hybrid",
    "datasets": [
      {
        "id": "primary-dataset",
        "name": "Primary Data Store",
        "type": "structured",
        "schema": {
          "tables": ["users", "products"]
        },
        "semanticTags": ["user-data", "product-data"],
        "contentDomain": "e-commerce"
      }
    ],
    "inferenceRules": [
      {
        "id": "user-query-rule",
        "name": "Route User Queries",
        "condition": {
          "type": "keyword-match",
          "parameters": {
            "keywords": ["user", "customer", "account"]
          }
        },
        "action": {
          "type": "select-dataset",
          "target": "primary-dataset"
        },
        "priority": 10,
        "confidenceThreshold": 0.7
      }
    ]
  }
}

🔧 Tool Calling

Define tools and how they should be invoked: 

{
  "toolCalling": {
    "invocationStrategy": "pipeline",
    "tools": [
      {
        "id": "validator",
        "name": "Data Validator",
        "description": "Validates input data",
        "function": "validateData",
        "parameters": [
          {
            "name": "data",
            "type": "object",
            "required": true
          }
        ],
        "semanticPurpose": "data-validation"
      },
      {
        "id": "processor",
        "name": "Data Processor",
        "description": "Processes validated data",
        "function": "processData",
        "semanticPurpose": "data-processing"
      }
    ],
    "toolSelectionRules": [
      {
        "condition": {
          "type": "intent-match",
          "parameters": {
            "intents": ["validate"]
          }
        },
        "action": {
          "type": "invoke-tool",
          "target": "validator"
        }
      }
    ]
  }
}

✨ Complete Example

Here's a complete component definition: 

{
  "$schema": "../schemas/mcp-component-schema.json",
  "id": "weather-api-component",
  "type": "source-module",
  "name": "Weather API Component",
  "description": "Provides weather data and forecasts",
  "apiStructure": {
    "protocol": "rest",
    "baseUrl": "http://localhost:8080/api/weather",
    "endpoints": [
      {
        "name": "getCurrentWeather",
        "method": "GET",
        "path": "/current",
        "parameters": [
          {
            "name": "location",
            "type": "string",
            "required": true,
            "semanticRole": "location"
          }
        ],
        "semanticTags": ["weather", "current", "real-time"]
      }
    ]
  },
  "semanticContext": {
    "domain": "weather",
    "intents": [
      "get-weather",
      "check-weather",
      "weather-forecast"
    ],
    "keywords": [
      "weather",
      "temperature",
      "forecast",
      "climate",
      "conditions"
    ],
    "concepts": [
      "meteorology",
      "weather-data"
    ]
  },
  "capabilities": [
    {
      "name": "Current Weather",
      "type": "query",
      "description": "Get current weather conditions"
    }
  ],
  "metadata": {
    "version": "1.0.0",
    "author": "Weather Team",
    "created": "2025-01-15T00:00:00Z"
  }
}

✅ Validation

Always validate your component against the schema: 

npm run validate-schema
⚠️ Warning: Components that don't validate against the schema will not be loaded by the inference engine.

📝 Best Practices

  • Single Responsibility: Each component should have one clear purpose
  • Rich Metadata: Provide comprehensive semantic context
  • Clear Naming: Use descriptive IDs and names
  • Versioning: Always include version in metadata
  • Documentation: Write clear descriptions
  • Testing: Test your component with various intents
